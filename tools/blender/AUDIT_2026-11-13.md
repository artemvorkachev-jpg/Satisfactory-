# Аудит каталога ассетов — 2026-11-13

## Итог проверки

**Статус: НЕ ПОЛНЫЙ.** Прежний `COMPLETE_ASSET_CATALOG.md` — это хороший тематический план, но он не содержит поштучного реестра всех игровых зданий и предметов. Называть его полным каталогом нельзя.

Сверка выполнена по доступным страницам официальной Satisfactory Wiki (wiki.gg), включая категории Buildings, Items, Equipment, Flora, Resource Node и Creatures. Страницы wiki.gg в этой сессии выдавали 403 при открытии, поэтому использованы индексируемые выдержки поисковой выдачи; это не заменяет ручную проверку каждой страницы и внутриигрового Codex/build menu.

## Найденные пробелы в прежнем каталоге

1. Не было отдельного поштучного реестра 150 предметов категории Items.
2. Не были явно внесены некоторые небоевые инструменты/гаджеты и декоративно-функциональные предметы, например Build Gun, Color Gun, Boom Box и Cup.
3. Не был зафиксирован принцип «каждый предмет на конвейере — отдельный предметный меш»: перечень был только общей строкой.
4. Не было отдельного полного реестра материалов строительства и вариантов строительных деталей по всем семействам.
5. Ресурсные узлы были описаны общим пунктом, без поштучного списка типов и вариантов чистоты.
6. Флора и фауна были описаны категориями, но не поимённо; в списке могли смешиваться актуальные, удалённые и сезонные варианты.
7. Не был выделен полный реестр аудио-событий, их пространственного поведения и миксов.
8. Не было проверено соответствие каждого пункта конкретной версии игры. Версия и внутриигровой Codex должны быть зафиксированы перед объявлением реестра завершённым.

## Важное ограничение по предметам

В этом проекте каталогируется промышленное строительство, исследование, транспорт, окружение, ресурсы, инструменты и защитное/перемещающее экипирование. Боевые предметы и оружейные модели не входят в производственный план. Это не должно мешать полноте небоевой части игры.

## Обязательная структура поштучного реестра

Для каждого ассета нужна отдельная запись с полями:

- `asset_id` — стабильный уникальный ID;
- `display_name` — название;
- `game_category` — категория оригинальной игры;
- `asset_kind` — отдельный меш / вариант меша / модуль / сборка / предметный меш / эффект;
- `visual_variants` — все подтверждённые визуальные варианты;
- `dimensions_m` — подтверждённые габариты или статус `unverified`;
- `snap_points` — стыковочные точки;
- `collision_profile` — тип коллизии;
- `animation_set` — анимации;
- `audio_events` — связанные звуковые события;
- `lod_set` — LOD;
- `source_status` — источник и дата проверки;
- `model_status` — planned / blockout / reviewed / approved / exported / mobile-tested.

Не создавать фиктивные точные размеры по скриншотам. Если точные размеры не подтверждены, ставить `unverified` и делать сравнительный блок-аут по эталонной сетке.

## Порядок завершения аудита

1. Зафиксировать версию игры и список категорий Codex/build menu.
2. Снять поимённый перечень уникальных зданий, модулей, предметов, экипировки, ресурсов, существ и растений.
3. Сопоставить каждый пункт с существующей записью каталога; убрать языковые дубликаты и удалённый контент, отметить сезонные варианты отдельно.
4. Создать отдельную строку/ID для каждого визуально самостоятельного меша. Не объединять разные модели только потому, что они относятся к одному классу.
5. Проверить зависимости и физические соединения.
6. Только после закрытия поштучного аудита начинать серийное моделирование.
7. Для каждого ассета подготовить 3–4 самостоятельных дизайн-варианта, получить оценку пользователя, доработать выбранный вариант и только затем утверждать его как эталон семейства.
